Chapter 8

Use cases

Five jobs people actually use this for, each with the source that does it. Copy one, change the names, and you have the thing rather than an example of the thing.

1 — An architecture document your team will read

The problem: the diagram in the wiki is two years old, nobody knows who owns what, and it is a PNG so nobody can fix it.

Keep the diagram in the repository as text, next to the code it describes. Put ownership in the file so it is reviewed like anything else. Collapse the parts most readers do not need. 

flowchart LR
%%mp: theme slate-dark
%%mp: group data collapsed
  users[Customers] --> cdn[Cloudflare CDN]
  cdn --> gw[Kong API Gateway]
  gw --> orders[Order Service]
  subgraph data [Data platform]
    orders --> odb[(Orders DB)]
    odb --> etl[ETL Worker]
  end
  orders --> q{{Order Events}}
  q -.-> fulfil[Fulfilment Worker]
%%mp: node gw note="Every public request enters here. Terminates TLS
  and rate limits per tenant." owner="Platform" sla="99.99%"
%%mp: node orders note="Owns the order lifecycle. The only writer
  to the orders schema." owner="Commerce" tier="1"

Then: export SVG into the wiki, or the standalone HTML page so readers can click around it.

2 — Onboarding a new engineer

The problem: the architecture overview is forty boxes and means nothing to somebody on day two.

Add numbered steps. The diagram becomes a guided tour that a new joiner can take alone, at their pace, without booking anybody's time.

%%mp: step 1 title="Start at the edge" focus=users,cdn
  note="Most catalogue reads never reach us at all."
%%mp: step 2 title="One way in" focus=gw
  note="Authentication, rate limiting and routing all happen here.
  Nothing else is exposed."
%%mp: step 3 title="Where orders live" focus=data
  note="Naming a group focuses everything inside it."
%%mp: step 4 title="Everything else is asynchronous" focus=q,fulfil
%%mp: step 5 title="The whole picture"

Then: ⌘K → Present walkthrough, or send them a link ending ?step=1.

3 — An incident postmortem

The problem: the timeline is in a doc, the system diagram is somewhere else, and the reader has to hold both in their head.

Two diagrams in one document. A timeline for what happened, and a flowchart of the path that broke, with the failure marked.

timeline
  title SEV-1 checkout outage, 4 September
  section Detection
    14.02 : order-service v4.18 deployed
    14.06 : Checkout error rate crosses the SLO
    14.09 : On-call paged
  section Mitigation
    14.31 : Rollback started
    14.49 : Declared resolved

And the path, with the cause where it actually was:

flowchart LR
  gw[API Gateway] --> orders[Order Service]
  orders --> pool[(Connection pool)]
  pool --> db[(Orders DB)]
%%mp: node pool note="Sized for the old query. The new one holds a
  connection six times longer, so 200 connections were not enough."
  owner="Commerce"

Then: PNG into the postmortem doc. The note travels with the source, so the next person to open the file sees the finding.

4 — A design review

The problem: you are proposing a change and the reviewers cannot see what is different.

Two diagrams, same theme, same direction: before and after. Reviewers compare pictures instead of reading prose about pictures.

flowchart LR
%%mp: theme slate-dark
  subgraph before [Today: synchronous]
    a1[Checkout] --> b1[Fraud check]
    b1 --> c1[Payment]
    c1 --> d1[Order created]
  end
  subgraph after [Proposed: scored asynchronously]
    a2[Checkout] --> c2[Payment]
    c2 --> d2[Order created]
    d2 -.-> q2{{Fraud events}}
    q2 -.-> b2[Fraud scoring]
    b2 -.-> r2[Review queue]
  end
%%mp: node b1 note="380ms at p99, on the critical path for every order."
%%mp: node b2 note="Off the critical path. A flagged order is reviewed
  within minutes rather than blocking the shopper."

Then: paste both into the RFC, or present them side by side in full-bleed.

5 — A runbook that shows the decision

The problem: the runbook is a wall of numbered prose and it is 3am.

A flowchart of the decision, with the commands in the notes. Somebody half awake can follow a picture.

flowchart TD
  start([Alert: checkout p99 above SLO]) --> recent{Deploy in the last 30 min?}
  recent -->|yes| rollback[Roll back]
  recent -->|no| pool{Connection pool saturated?}
  pool -->|yes| scale[Scale the pool and the replicas]
  pool -->|no| upstream{Payment provider degraded?}
  upstream -->|yes| failover[Fail over to the secondary provider]
  upstream -->|no| escalate[Escalate to the secondary on-call]
  rollback --> verify{Recovered?}
  scale --> verify
  failover --> verify
  verify -->|no| escalate
  verify -->|yes| done([Monitor for 30 minutes])
%%mp: node rollback note="kubectl rollout undo deploy/order-service
  Takes about four minutes to drain."
%%mp: node failover note="Flip payments.provider to secondary.
  No deploy needed, effective in seconds."

Then: the standalone HTML page, pinned in the incident channel. It works with no tools installed and the notes are one click away.

The pattern in all five: the diagram lives as text, next to what it describes, and the explanation lives in the same file. That is the thing a drawing tool cannot give you.
